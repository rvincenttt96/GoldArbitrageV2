# اضافه کردن یک پلتفرم

سه قدم دارد. هیچ‌کدام نیازمند دست زدن به منطق استراتژی نیست.

## قدم ۱ — ثبت پلتفرم در `config/platforms.toml`

```toml
[platforms.newvenue]
display_name = "New Venue"
enabled = false        # فعلاً حتی قیمت هم نگیرد
verified = false       # حتی وقتی enabled شد، اجازهٔ سفارش ندارد
adapter = "adapters.newvenue.client:NewVenueClient"
capabilities = []
quote_ttl_seconds = 30.0

[platforms.newvenue.buy_fee]
rate = "0.005"
basis = "cash"         # یا "gold" اگر کارمزد را به وزن طلا می‌گیرد

[platforms.newvenue.sell_fee]
rate = "0.005"
basis = "cash"
min_billable_mg = 0    # اگر حداقل وزن مشمول دارد، اینجا

[platforms.newvenue.limits]
min_order_mg = 10
step_mg = 10
```

تفکیک `enabled` از `verified` عمدی است:

| enabled | verified | نتیجه |
|---|---|---|
| false | — | کاملاً غایب |
| true | false | قیمت می‌دهد و در Recorder می‌آید، ولی هرگز سفارش نمی‌گیرد |
| true | true | قابل معامله |

یعنی یک پلتفرم جدید می‌تواند هفته‌ها داده جمع کند بدون اینکه بتواند پول از دست بدهد.

## قدم ۲ — نوشتن آداپتور

از `adapters.base.GoldAdapter` ارث ببرید. پنج متد اجباری: `login`، `get_quote`،
`get_inventory`، `buy`، `sell`.

قواعدی که قابل مذاکره نیستند:

- **آداپتور خودش تصمیم می‌گیرد پاسخش موفق بوده یا نه.** هرگز dict خام به اجراکننده ندهید. یک
  پارسر مشترک نمی‌تواند خطای گلدیکا را از خطای میلی تشخیص دهد و بالاخره روی یک سفارش زنده اشتباه
  حدس می‌زند.
- **پاسخ ناشناخته یعنی شکست، نه موفقیت.**
- **روی POST سفارش هرگز retry نکنید.** خطای شبکه یعنی نمی‌دانیم؛ `UncertainExecutionError`
  بدهید و بگذارید بالادست توقف کند.
- اگر پلتفرم فقط یک قیمت مرجع می‌دهد (مثل میلی‌گلد)، همان را برای هر دو side برگردانید و
  `two_sided_quote` را در capabilities **نگذارید**. اسپردش در کارمزد است و لایهٔ استراتژی باید
  این را بداند.
- مقادیر همه‌جا **میلی‌گرم صحیح**‌اند و پول **Decimal تومان**.

## قدم ۳ — تأیید با یک سفارش واقعی کوچک

`verified = true` فقط بعد از این مجاز است:

1. یک خرید در حداقل حجم مجاز، و تطبیق تغییر موجودی با تخمین.
2. یک فروش در همان حجم، و همان تطبیق.
3. مقایسهٔ کارمزد واقعی فاکتور با `fee_tmn()` — اگر نخواند، `FeeSpec` غلط است نه فاکتور.

# آنچه برای طلا۳۰ و ملی‌گلد لازم دارم

هر دو دامنه پشت سپر بات **ArvanCloud** هستند و از خارج ایران قابل بررسی نیستند:

- `melligold.com` — چالش کوکی ۳۰۷ (`__arcsco`)؛ صفحهٔ لندینگ بعد از حل چالش می‌آید ولی مسیرهای API
  همچنان ۳۰۷ می‌دهند.
- `tala30.ir` — دامنه resolve می‌شود، origin از این‌جا ۵۰۴ می‌دهد.

پس endpointها را نمی‌شود از بیرون کشف کرد. برای هر پلتفرم این را لازم دارم:

**یک فایل HAR** از DevTools مرورگر (تب Network، گزینهٔ Export HAR) در حالی که وارد حساب شده‌اید و
این کارها را انجام می‌دهید:

1. ورود به حساب
2. باز کردن صفحهٔ خرید و فروش و ماندن روی آن تا چند بار قیمت تازه شود
3. مشاهدهٔ موجودی ریالی و موجودی طلا
4. **یک خرید واقعی در حداقل حجم** (مثلاً ۱۰ سوت) تا کل چرخهٔ سفارش دیده شود
5. **یک فروش واقعی در همان حجم**
6. اگر صفحهٔ «سوابق معاملات» دارد، باز کردنش

از HAR این چیزها را استخراج می‌کنم و آداپتور را می‌نویسم:

| چه چیزی | چرا |
|---|---|
| مسیر و پی‌لود لاگین، محل توکن | `login()` |
| endpoint قیمت و اینکه یک قیمت می‌دهد یا دو تا | `get_quote` و capability `two_sided_quote` |
| فیلد انقضا یا TTL قیمت | `quote_ttl_seconds` و بررسی کهنگی |
| **واحد مقدار** — گرم، سوت، میلی‌گرم؟ | مهم‌ترین چیز. اشتباه در واحد یعنی ۱۰۰ برابر خطا در حجم |
| اینکه سفارش یک‌مرحله‌ای است یا init/confirm | capability `invoice_flow` |
| کارمزد دقیق در فاکتور | کالیبره کردن `FeeSpec` |
| هدرهای لازم (`X-Platform` و مشابه) | آداپتورهای موجود بدون اینها ۴۰۳ می‌گیرند |

**قبل از فرستادن HAR، توکن‌ها و کوکی‌ها را پاک کنید.** من فقط به شکل درخواست و پاسخ نیاز دارم، نه
به اعتبارنامه. اگر راحت‌تر است، فقط خروجی «Copy as cURL» هر درخواست به‌علاوهٔ بدنهٔ پاسخ هم کافی است.

اگر HAR ممکن نیست، جایگزین: یک VPS ایران بدهید تا خودم کشف کنم.
